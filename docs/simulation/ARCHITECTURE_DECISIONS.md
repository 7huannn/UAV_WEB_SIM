## ADR-002 — One authoritative fixed-step coordinator

- **Status:** Accepted for implementation via user approval of P1-v1 on 2026-11-19 ("I approve"); implemented; validation/disposition recorded in PHASE_HANDOFF. The user formally accepted the scoped Phase 1 result, limitations and deferred issues on 2026-11-19.
- **Problem:** `DroneDynamics.advance()` owns environmental time while direct `step()` omits weather stepping; reference commands integrate at rendered cadence. Reset/replay consumers read aircraft-owned time ([Dynamics](../../src/simulation/DroneDynamics.ts), lines 315–325, 383–405; [World](../../src/scene/World.ts), lines 1136–1145, 1243).
- **Options:** leave scheduling in aircraft and add callbacks; create an independent weather clock; extract the existing scheduler into one focused coordinator.
- **Selected approach:** extract one coordinator owning integer tick, derived seconds, accumulator, admission/drop accounting and exactly-once weather/aircraft/transport updates. Existing public advance/single-tick methods delegate to it. Physical kernel consumes explicit completed-step environmental data/time and does not schedule itself. Both manual command paths consume held input once per fixed tick; retain their current coordinate mappings.
- **Reasoning:** moves ownership to the layer that coordinates systems while retaining the validated aircraft/controller. Preserve 0.004 s stepping and 0.1 s admission limit; overload is observable slowdown, not permission to enlarge dt. Retain the current normal-advance convention of wind sampled at the resulting tick time. The coordinator notifies World on resume to discard its host wall-time baseline; paused intervals cannot enter the first resumed frame. A 1e-12 s comparison tolerance handles floating accumulator boundaries, not a variable timestep.
- **Affected systems:** focused simulation coordinator; Dynamics scheduling/time/reset interfaces; World loop/input/hide handling; Session timestamp consumers; tests and existing browser stepping helpers.
- **Trade-offs/rejected alternatives:** small API/caller migration is necessary. Reject duplicate weather stepping, a second plant, unbounded catch-up, render-owned cloud integration, and a worker before profiling justifies one.
- **Known limits:** browser input polling latency remains; holding a sampled command across catch-up ticks does not recreate missing device samples. Same-runtime equal-tick determinism does not imply real-time hardware capacity. Direct `step()` weather semantics intentionally become consistent; explicit thrust overrides remain supported.
- **Validation:** P1-A/B/C/F; characterization fixtures, tick counters, irregular render schedules, pause/hide/reset, invalid elapsed inputs, both mission completions and manual fixtures. No changes to gains, force/motor/contact equations or scoring.
- **Revisit:** multi-aircraft scheduling, measured worker need, or a changed fixed-step model. Such changes require new evidence/contract, not an extension hidden inside Phase 1.

## ADR-003 — Explicit, shared wind sampling with bounded approximations

- **Status:** Accepted for implementation via user approval of P1-v1 on 2026-11-19 ("I approve"); implemented; validation/disposition recorded in PHASE_HANDOFF. The user formally accepted the scoped Phase 1 result, limitations and deferred issues on 2026-11-19.
- **Problem:** aircraft samples local wind, atmosphere samples origin, vegetation reuses aircraft wind. Same parameter names do not ensure same field sample ([Weather](../../src/weather/Weather.ts), lines 89–104; World lines 1256–1265; [atmosphere](../../src/scene/atmosphere.ts), line 171).
- **Options:** one global vector; duplicate the field in arbitrary shaders; shared CPU evaluator plus consumer-appropriate sampling.
- **Selected approach:** one evaluator of explicit parameter snapshot/seed/model version/time/world position. Aircraft uses physical position; vegetation uses stable tile centres; current rain/cloud rendering uses declared bulk reference samples until its owner phase introduces finer models. Snapshot sampling supports replay without mutating live Weather.
- **Reasoning:** preserves the current deterministic model while correcting hidden dependencies. CPU tile sampling reuses bounded storage and avoids a second independently drifting GPU wind formula. Each tile has a distinct material uniform with shared geometry/shader programs; visible/depth materials share that tile vector, so per-draw uniform updates do not rely on a shared global wind value. Bending phase is a vegetation response, not a replacement wind field.
- **Affected systems:** Weather, Dynamics sample call, World presentation adapters, grass/clump uniforms, atmosphere transport/sampling and focused tests.
- **Trade-offs:** tile and bulk approximations sacrifice within-region variation for bounded cost. For current field, component errors from tile-centre offsets are bounded by `turbulence * (0.13*abs(deltaZ), 0.064*abs(deltaX), 0.17*abs(deltaX))` in X/Y/Z, using the sine derivative bound and current coefficients. New field formulas invalidate this bound and require new tests.
- **Rejected alternatives:** aircraft-driven grass, unstated origin defaults, per-blade CPU updates, or camera-dependent authoritative wind.
- **Known limits:** current field ignores height; naming cloud sample heights does not add shear. Legacy cloud transport uses 0.3 of sampled bulk wind and remains a declared visual approximation. Current rain trajectories still reposition under changing wind; Phase 4 owns that defect. This ADR does not claim individual droplets already follow local wind.
- **Validation:** P1-E/H; shared point samples, analytical tile bounds, fixed-location samples unchanged by aircraft/camera movement, visible/depth shader consistency, paused READY preview, replay snapshots and bounded per-tile cost.
- **Revisit:** accepted Phase 5 wind/shear model or Phase 4 trajectory work, or profiling showing tile sampling too costly. Preserve field equivalence and version provenance under any optimization.

## ADR-004 — Angular weather transitions preserve existing scalar response

- **Status:** Accepted for implementation via user approval of P1-v1 on 2026-11-19 ("I approve"); implemented; validation/disposition recorded in PHASE_HANDOFF. The user formally accepted the scoped Phase 1 result, limitations and deferred issues on 2026-11-19.
- **Problem:** scalar blending sends 359°→1° through 180° ([Weather.step](../../src/weather/Weather.ts), lines 81–84).
- **Options:** scalar interpolation; wind-vector interpolation; shortest signed angular interpolation with existing speed blending.
- **Selected approach:** normalized towards direction, shortest signed angular difference, positive rotation for exact 180° ties; use the existing 2 s exponential response. Keep scalar speed/gust/turbulence and wetness response constants unchanged. Check equivalent 0°/360° endpoints.
- **Reasoning:** fixes unintended rotation without introducing speed attenuation from vector interpolation. Direction transition policy is not an atmospheric turbulence model.
- **Affected systems:** Weather transition; logs/replay interpolation policy; tests. Product input units and towards convention stay unchanged.
- **Trade-offs/rejected alternatives:** a half-turn needs an arbitrary but explicit deterministic tie. Vector interpolation can reduce speed toward zero during a reversal; reject that as an unrequested behavioural change.
- **Known limits:** shortest angle is a scenario transition policy, not a measured weather-front model. Only supported daytime solar parameters are currently used; no midnight interpolation/night model is added.
- **Validation:** P1-D, both wrap directions, 0°/360°, exact ties, sample continuity, fixed-step cadence and no unauthorized parameter changes.
- **Revisit:** an explicitly approved model of evolving wind vectors or fronts, with speed/turn dynamics justified and existing recordings versioned.

## ADR-005 — Snapshot-based presentation and backward-compatible replay

- **Status:** Accepted for implementation via user approval of P1-v1 on 2026-11-19 ("I approve"); implemented; validation/disposition recorded in PHASE_HANDOFF. The user formally accepted the scoped Phase 1 result, limitations and deferred issues on 2026-11-19.
- **Problem:** recorded-state playback restores weather but environmental render time/wind come from paused live aircraft; cloud history survives reset and seeks. Existing frame time is attempt-relative and does not recover original absolute wind phase (World lines 947–970, 1147–1265; [Session](../../src/training/Session.ts), lines 149–180, 523–565; [records](../../src/training/records.ts), lines 290–316).
- **Options:** resimulate flights from logs; mutate live Weather during replay and add exceptions; select a complete environmental presentation snapshot separately from live authoritative state.
- **Selected approach:** same renderer-facing snapshot shape for live interpolation and replay selection. Fixed ticks advance environment transport; rendering only reads it. Add a validated optional environment block with its own version to newly produced schema-1 records: initial epoch/model/seed/state and sufficient per-frame time/tick/transport. Preserve existing channels and immutable sealed payloads. Freeze/preserve live context on entry and restore it exactly on exit.
- **Reasoning:** enables seek-order independence without pretending sparse RC/state recordings can recreate the full flight. Versioned provenance supports later changes without silently reinterpreting earlier trajectories.
- **Affected systems:** World, coordinator/environment snapshots, atmosphere/vegetation adapters, Session recording, records validation/interpolation, minimal replay limitation presentation, tests.
- **Trade-offs:** bounded additional record size and interpolation/cache work. New continuous snapshot values interpolate adjacent recorded states; discrete fields are held and directions use shortest arc. Record exact rules with field definitions during implementation. No per-drop history or exact rotor phase is required in Phase 1.
- **Legacy policy:** absent extension uses logged weather/wetness/seed and relative time, explicitly zero-origin wind phase, and deterministic reconstructed bulk transport from logged history. A bounded per-record prefix cache is acceptable. Original phase/history is unrecoverable; product language must identify approximate legacy environment. Do not alter/reseal adapted originals. A malformed present extension rejects; it is not treated as absent.
- **Rejected alternatives:** hiding missing provenance, rewriting old checksums, reconstructing from live weather/seek history, recording unbounded every-frame particle state, or full flight resimulation.
- **Known limits:** recorded weather is sampled, not a complete meteorological history. New playback matches the recorded/interpolated snapshot model; legacy cannot be claimed to reproduce the original sky or wind phase. Cross-GPU pixel identity is not promised.
- **Validation:** P1-F/G/H; same timestamp via varied seek paths/speeds, captured keyframe agreement, interpolation boundaries, malformed/unsupported blocks, unchanged old exports/checksums/annotations, complete live restoration and bounded cache/record size.
- **Revisit:** schema evolution, new wind/transport models, or validated resimulation requirements. Introduce a new version/ADR and preserve old meaning rather than overwrite models in place.

## ADR-006 — Explicit fresh-run, READY, pause and continuation semantics

- **Status:** Accepted for implementation via user approval of P1-v1 on 2026-11-19 ("I approve"), including the wetness policy below; implemented; validation/disposition recorded in PHASE_HANDOFF. The user formally accepted the scoped Phase 1 result, limitations and deferred issues on 2026-11-19.
- **Problem:** aircraft reset rebuilds aircraft state but preserves Weather; READY synchronizes parameters without resetting wetness/cloud history. Consequently selected weather alone does not determine starting presentation (Dynamics lines 80–94; World lines 804–807, 900–970).
- **Options:** preserve all history implicitly; reset every value to clear/dry; provide distinct fresh-run initialization and continuation/snapshot restore.
- **Selected approach:** fresh run/H reset retains selected target/seed and existing guards, resets clock/accumulator/drop counters/transport, initializes current=target and wetness=current rain (equilibrium of the existing first-order wetness model), and records that same state. READY edits synchronize preview and initial snapshot at frozen time. Ordinary pause and continuation preserve existing environmental history; started weather edits affect target only and remain logged. Preserve mission/input restrictions and hooks. Replay context restore is continuation, not fresh reset.
- **Reasoning:** deterministic rainy/dry scenario initialization avoids a previous flight deciding a new attempt's surface appearance. It uses the current model's equilibrium rather than an unexplained new wetness constant. Distinct semantics prevent opening conditions or returning from replay from resetting the world.
- **Affected systems:** coordinator reset/snapshot APIs, World READY/attempt/replay lifecycle, minimal navigation caller routing, Session metadata and tests. No new learner control or weather mapping.
- **Trade-offs/rejected alternatives:** fresh rainy runs will begin visually wet instead of depending on previous simulation duration. Reject silent wetness carry-over and automatic clear-weather reset. An explicitly dry-starting storm is a later scenario option, not a new Phase 1 setting.
- **Known limits:** normalized wetness is artistic, not actual water depth. Surface evolution retains 7/32 s response; realistic accumulation/drainage is outside scope. Existing visual appearance may change at initialization for correctness, without material retuning.
- **Validation:** P1-F/G/H; two fresh starts agree, READY snapshot matches preview, pause cannot dry/wet surfaces, resume retains transport, active reset is rejected, practice/demo preferences and mock locks persist, replay exit restores paused state exactly.
- **Revisit:** approved persistent-world scenarios or calibrated surface model. Distinguish intentional continuous weather from independent attempts and version initial conditions.

## ADR-007 — Unified art direction with staged evidence, not premature technique selection

- **Status:** Active governance for standards/review boundaries. P3-v1 and P3-v2 were approved, but Phase 3 remains incomplete after the isolated P3-v2 candidate failed whole-scene visual review. P3-v3 is proposed, not approved. Phase 3 human aesthetic acceptance and Phase 4–6 work remain unauthorized.
- **Problem:** sky, fog, ground matte, cloud/rain optics and lighting use independent mappings; technical passes alone do not establish cohesive visuals or natural motion.
- **Options:** layer cosmetic fixes; mandate volumetrics/new renderer now; define persistent standards and choose bounded techniques in the owning phase from controlled comparisons.
- **Selected approach:** DESIGN_STANDARDS governs color, light, atmospheric depth, material state, motion, optics and camera invariants. Phase 3 resolves horizon/extinction before Phase 4 rain optics. Each visual change requires observed matched scenes and moving sequences. Retain current renderer/physics unless evidence proves a replacement necessary.
- **Evidence/reasoning:** source confirms independent horizon fades/extinction, camera-relative/repeating rain, and shared but inconsistent wind consumers. Retained screenshots show artifacts but are historical and cannot prove future improvements. User explicitly requires restraint, continuity and motion review.
- **Affected systems:** atmospheric/terrain/rain/vegetation presentation in future authorized phases; capture protocol and quality reports now.
- **Trade-offs/rejected alternatives:** expert review remains necessary; numerical image metrics alone do not establish aesthetics. Reject fog masking, extra particles as a substitute for optics, camera-specific patches, arbitrary aircraft forces, and competing old/new effects.
- **Known limits:** hardware targets, visual baselines and optical thresholds require measured representative scenes/devices. No new captures or aesthetic acceptance are claimed by planning. Legacy cloud/rain approximations remain tracked until their phases.
- **Validation:** named static/moving scene protocol; five-dimension gate, source/condition manifests, CPU/GPU provenance and anti-patchwork review. Required unobserved categories remain UNVERIFIED, not N/A.
- **Revisit:** observed evidence or user direction warrants changing art/fidelity targets. Propose updated standard/ADR and consequences before implementation; revalidate affected earlier gates.

## ADR-008 — Preserve the illustrative plant and make model semantics explicit

- **Status:** Accepted via the user's explicit approval of P2-v1 on 2026-11-19; implemented and scoped gates validated in [PHASE_2_HANDOFF](PHASE_2_HANDOFF.md). The user formally accepted the scoped Phase 2 result on 2026-11-19. ADR-002–006 remain implemented and their Phase 1 result was formally accepted with its limitations/deferred issues.
- **Problem/evidence:** `parameters.ts` has `dragArea` but the actual equation in `DroneDynamics.integrate` has no separate Cd; `arm` is an X/Z offset, public `torque` is a controller request, and net `force` excludes contact correction. These can be misread as measured geometry, radial distance or achieved wrench. All physical coefficients remain illustrative.
- **Options:** add unsupported aerodynamic coefficients/moments; rename stored fields/rewrite the plant; preserve numerical behavior and document an explicit SI/frame/force ledger with independent analytical checks.
- **Selected approach/reason:** treat `dragArea` as effective axis-wise Cd·A, retain current keys/values and one production kernel, and separately account for rotor moments, existing damping, gyroscopic coupling and contact. Define requested/clipped/actual wrench instead of changing old telemetry meanings. Validate the chosen model; do not claim real-aircraft calibration.
- **Affected files:** dynamics diagnostics, semantic parameter comments, focused physics tests, assumptions and governance; detailed equations/thresholds are owned by P2-v1 in MASTER_PLAN.
- **Trade-offs/rejected alternatives:** leaves a simplified CG drag/fixed-density/ideal-state aircraft with no inflow or calibrated aero moments. Reject new forces or parameter fitting without data; retain advanced fidelity in Phase 5.
- **Validation:** P2-A–D/H, invariant traces and source review; constant/co-rotated velocity/drag, dissipative air-relative work, motor/mixer closure and timestep refinement. Real-data gates remain UNVERIFIED.
- **Revisit:** identified aircraft/held-out data, failed required equation checks, or a new accepted fidelity target. Any changed law/coefficient requires a reviewed revision, provenance and compatibility plan before implementation.

## ADR-009 — Optional completed-step diagnostics and a single override guard

- **Status:** Accepted via explicit P2-v1 approval on 2026-11-19; implemented and scoped gates validated in [PHASE_2_HANDOFF](PHASE_2_HANDOFF.md). The user formally accepted the scoped Phase 2 result on 2026-11-19.
- **Problem/evidence:** existing telemetry cannot distinguish requested torque, clipped mixer authority and lagged motor achievement. Re-running the controller to inspect it would advance integrals/derivative state. `Simulation.step(thrust?)` currently accepts malformed/nonfinite overrides before indexing them in the plant, permitting state poisoning.
- **Options:** a separate diagnostic simulator; always-recorded per-tick channels/UI; one disabled-by-default reusable diagnostic result in the actual calculation path plus a shared entry guard.
- **Selected approach/reason:** capture already-computed values once into bounded optional completed-step diagnostics, preserving existing fields. Test/script collectors stream at no more than 50 Hz with P2-J limits, never extend production attempts. Validate exactly four finite override numbers in `Simulation.step` before any state mutation; preserve finite clamping. Use the same kernel for test-only smooth timestep studies; production remains fixed 250 Hz.
- **Affected files:** existing Dynamics, Simulation (guard only), focused tests/script and documents. No new scheduler, Weather model, record schema, UI, dependencies or physics engine.
- **Trade-offs/rejected alternatives:** disabled instrumentation still needs a measured branch cost; enabled diagnostics require careful sample-stage labeling. Reject calling controller twice, per-tick serialization, unbounded arrays, a generic observer/event framework or a duplicate force implementation.
- **Validation:** P2-A/B/C/D/H/J; diagnostic on/off state equality, analytical closure, no-state-change rejection through both public stepping entry points, fixed-step preservation, matched cost and bounded output. Source-identified baseline is the accepted working tree, not only old HEAD.
- **Revisit:** justified durable diagnostic product requirements or a benchmark failure; propose a bounded revision, do not silently enlarge scope or runtime storage.

## ADR-010 — Measure actuator saturation and recovery before changing control

- **Status:** Accepted via explicit P2-v1 approval on 2026-11-19; diagnostic/validation approach implemented and scoped gates validated in [PHASE_2_HANDOFF](PHASE_2_HANDOFF.md). The user formally accepted the scoped Phase 2 result on 2026-11-19; controller redesign/retuning remains outside this acceptance.
- **Problem/evidence:** current position/rate integral clamps and motor clipping are not allocation-aware anti-windup. The controller requests up to 6 N·m per torque axis, while its theoretical fixed-collective hover yaw limit is about 3.67749 N·m before lag. This proves possible infeasibility, not observed instability. No derivative filter or sensor model exists.
- **Options:** blindly tune gains/add damping; immediately adopt another flight stack's controller; retain laws/gains and measure explicit demanded/clipped/actual wrench and bounded-integral recovery first.
- **Selected approach/reason:** retain the existing cascade and all gains under P2-v1. Require calm/command/wind/saturation/long-run gates with numerical targets and traceable conditions; expose failure honestly. A failed gate requiring anti-windup, filtering, allocation, gains or force changes triggers a concrete P2-v2 proposal/approval before the remedy. Complete unaffected authorized validation meanwhile.
- **Affected systems:** controller diagnostic capture, analytical mixer/recovery fixtures, performance/evidence and future change control. No new raw-throttle/rate mode, feed-forward or visual aircraft motion.
- **Trade-offs/rejected alternatives:** Phase 2 may finish validation with an unresolved required failure and need a revised contract; that is preferable to silently changing accepted dynamics or calling bounded integrals a complete stability proof. Software targets do not establish robust control over every valid weather input.
- **Validation:** P2-E/F/G/H; actual rotor clipping during the defined pulse, no release-time integral/motor reset, commanded feasibility residuals, measurable return to hold, both missions and manual behavior. Missing hardware/logs remain unverified calibration, even if all software gates pass.
- **Revisit:** reproducible failure, measured sensor/actuator behavior or an accepted expanded envelope. Record exact correction, held-out comparison, new model/controller provenance, regression and cost thresholds in the revision; do not copy external gains as calibration.

## ADR-011 — One atmospheric radiance/visibility state before rain optics

- **Status:** P3-v1 and the [P3-v2 amendment](PHASE_3_REVISION_PROPOSAL.md) were explicitly approved on 2026-11-19. The required isolated prototype tested a shared local sky/path source but failed P3-D/I and was not selected for production. Repeated retained-build profiles put the original one-run P3-J regression in doubt; final matched profiling is pending. The [P3-v3 alternative](PHASE_3_ALTERNATIVE_PROPOSAL.md) is proposed, not approved. Final ADR/visual acceptance is pending.
- **Problem/evidence:** ATM-01/02 and LIGHT-01: isolated Ground/Pilot/FPV/Overview captures show the nearly white lower band persists in `sky-only`, `no-clouds` and `no-fog`; the camera-height context alpha created a separate hard terrain termination. The initial shared MOR/context repair leaves a measured 19% adjacent-row linear-luminance change at the sky/ground boundary. One software profile also exceeds P3-J. See the interim handoff and visual board.
- **Options:** increase fog/grade to hide the band; add volumetrics or a replacement renderer immediately; isolate contributors, then derive one daytime atmospheric/solar/visibility state from the existing EnvironmentSnapshot and reuse it across sky, surface transfer, cloud light and reflection invalidation.
- **Selected proposal:** diagnostic isolation first; a bounded shared linear-light optical transfer and sky/path radiance, preserving one Weather/Simulation owner and current renderer where it meets evidence. Visibility has a declared 5% contrast convention. Terrain context is repaired at the shared geometry/transfer boundary, without per-camera overrides. Reflection updates are driven by meaningful radiance inputs and measured cost. Rain-level editing ceases to change solar time. Details and P3-A–L gates are in P3-v1.
- **Trade-offs/rejected alternatives:** the proposed homogeneous extinction is an illustrative local-air approximation, not measured atmospheric chemistry or planetary multiple scattering. Existing cloud shells may suffice or may fail expert review; full volumetrics, LUT sky, new renderer, arbitrary silhouettes, exposure changes and rain rendering require separate evidence and controlled revision. Do not hide source defects with fog, grading or brightness.
- **Affected modules after approval:** atmosphere.ts, World.ts, weatherPresets.ts, focused tests/evidence; no physical plant, recording schema, pilot optics, missions, assets or Phase 4 rain trajectories.
- **Validation:** isolated before/after component frames, quantitative visibility/horizon/solar/reflection checks, static and moving multi-camera/weather scenes, expert art rubric, regression/performance and anti-patchwork audit. User acceptance of a final Phase 3 result remains a later decision.
- **Revisit:** P3-v2 approval authorized a minimal isolated experiment; its visual failure triggers the controlled P3-v3 proposal. No new production sky replacement or additional atmosphere technique is authorized until that proposal is explicitly approved.

## Change procedure

For a new decision, record ID/status/date/phase, problem, evidence, options, selection/reason, affected files, trade-offs, rejected alternatives, limitations, validation, and revisit trigger. On approval, record who approved and the actual instruction/date; do not fill a fictional approval. On implementation, link source and handoff evidence. If a later phase contradicts an earlier contract, stop dependent work, document the conflict and controlled revision, update MASTER_PLAN/tests, obtain required review and revalidate. A temporary approximation must state its purpose, owner phase, limits and removal/revisit condition.
