## 1. Intended outcome and preservation boundary

Deliver one coherent daytime atmosphere for the existing browser renderer: sky radiance, cloud appearance, sun and ambient illumination, aerial perspective, terrain/context termination, material response and reflections must describe the **same** weather, solar direction and visibility. The result should read as a restrained, credible outdoor training environment from ground eye height through elevated cameras and moving flight, not as individually polished effects. Keep the court dimensions, field/mission bounds, drone scale, fixed pilot station and 55° pilot optics, camera controls, UI identity, Three.js/ACES/sRGB pipeline unless evidence justifies a narrowly reviewed change. Keep one Simulation clock, Weather field, snapshot/replay contract and DroneDynamics plant. No physics, controller, wind formula, motor, scoring, mission, record-schema, input or camera-behavior change is authorized by P3-v1.

Phase 3 owns ATM-01/02, LIGHT-01 and WEATHER-01. It does **not** own rain drop placement, streaks, spawning, fall model, quality-invariant rain density or splash optics (RAIN-01/02, Phase 4). Existing rain remains a limitation in Phase 3 visual reviews. No night sky, surveyed surrounding facility, new flight area, new weather-force coupling, or real-aircraft validation is claimed.

Source mechanisms to isolate before choosing technique:

1. In [atmosphere.ts](../../src/scene/atmosphere.ts), Three.js Sky has turbidity/rayleigh driven by cloud cover; its radiance is independent of the separate constant-color FogExp2. Cloud fragments discard below view-ray Y=.008, fade over .008–.055 and substitute a fixed pale lower color over .01–.17; shell intersections are clamped at the same low angle. These operations can create a pale, cloud-free strip.
2. In [World.ts](../../src/scene/World.ts), the noninteractive 600 m turf context fades alpha from distance 35+4×camera-height to 200+4×camera-height. Its rectangular extent and camera-height-dependent threshold can expose the renderer clear color or a long straight edge. Court geometry and official 60×42 m grass remain separate.
3. Visibility currently sets FogExp2 density to 0.75 / max(50, visibility), without a declared contrast convention. Fog applies to rendered surfaces while sky/cloud shaders use separate horizon logic. The clear color is another pale constant. Thus visible distance, sky horizon and distant turf do not share a transfer law.
4. Sun direction, direct intensity, hemisphere color/intensity, sky parameters, cloud tint and fog color are independently mapped. Cloud shading uses fixed bright/dark endpoints; material response and terrain wetness need the same light context. The PMREM scene reuses sky/cloud materials, but refresh in World is keyed only to target solar time/cloud and waits for settling; rain/visibility radiance changes and intermediate transitions can leave reflections stale. Verify actual capture timing and material effect before altering it.
5. [weatherPresets.ts](../../src/training/weatherPresets.ts) rain-level editing changes rain, cloud, visibility **and timeOfDay**. Preset scenario changes may intentionally include time; editing precipitation alone must keep the current solar time. The accepted 2 s weather response and 7 s/32 s wetness response are preserved.
6. Existing concrete/grass textures are tagged sRGB or data as appropriate in World, with ACES exposure .95 and sRGB output. ShaderMaterial clouds include tone-mapping/color-space chunks. Audit custom material and PMREM color spaces with diagnostic neutral patches before changing albedos, exposure or grading; the current screenshot alone cannot identify a color-space defect.

## 3. Visual Reference and Art Direction Baseline — proposed for approval

Use these as **phenomenological references**, not literal scene plates, geolocation claims or license to add landmarks. Record reference image/page, viewing direction, lighting/weather, what is transferable, and what is outside this simulator's 45×27 m court/60×42 m ground. During implementation, place matched simulator frames alongside them and annotate deviations; do not copy or ship reference images as assets.

- **Clear / scattered cloud:** [WMO International Cloud Atlas, Cumulus mediocris](https://cloudatlas.wmo.int/cumulus-mediocris.html) and [WMO cloud identification guide](https://cloudatlas.wmo.int/en/cloud-identification-guide.html). Learn varied cloud silhouette, flatter/darker bases, gaps of chromatic sky, and scale decreasing toward distance. Do not reproduce a specific photographed cloud.
- **Broken overcast:** [WMO stratocumulus detached elements](https://cloudatlas.wmo.int/en/stratocumulus-stratiformis-occur-sheet-layer-detached-elements.html). Learn broad but uneven cover, soft volumetric cues through light and tone, restrained gray-white base variation and visible openings; not a repeated horizontal texture band.
- **Dense rain-cloud ceiling, with rain redesign deferred:** [WMO Nimbostratus](https://cloudatlas.wmo.int/nimbostratus-ns.html). Learn obscured direct sun, subdued but not uniformly white ambient, soft/diffuse base, and reduced distant contrast. This is a cloud/lighting reference for Phase 3; falling precipitation is Phase 4.
- **Aerial perspective and terrain depth:** [NASA Earth Observatory's ground-view mountain comparison](https://earthobservatory.nasa.gov/blogs/elegantfigures/2013/10/22/how-to-make-a-true-color-landsat-8-image/). Learn that distant land loses contrast and shifts toward path radiance gradually while near material retains identity. Do not import its mountains, biome, scale or palette into the UAV court.
- **Optical/technical reference, not a mandated renderer:** [WMO meteorological visibility definition](https://www.weather.gov/media/epz/mesonet/CWOP-WMO8.pdf) uses the 5% contrast convention; [Bruneton and Neyret](https://onlinelibrary.wiley.com/doi/abs/10.1111/j.1467-8659.2008.01245.x) explain sky/aerial-perspective coupling; [Three.js color management](https://threejs.org/manual/pages/color-management.html) explains linear working color and shader output. The repository's small ground scene does not justify importing a full planetary scattering engine without measured need.

Art-direction target: a believable local training field in daylight, with sky chroma and solar warmth tied to conditions; a legible but physically sized aircraft and markings; tactile concrete/turf that retain identity through wet/cloud transitions; depth carried by consistent extinction and light, not by a white veil; natural cloud hierarchy and motion without obvious texture stamping; no cinematic bloom, exaggerated saturation, mirror wetness, invented skyline or arbitrary detail noise. Expert review must evaluate the *whole image and sequence*—composition, light temperature, material identity, depth, restraint and continuity—not merely numerical similarity to a reference.

## 4. Proposed rendering architecture and decision order

**Stage A — instrument and isolate root causes before visual changes.** On the accepted build, create a bounded capture/diagnostic runner (not a learner UI) at identical snapshot/camera/exposure. Capture combined, sky-only, clouds-only, terrain/context-only, no-context, no-fog, no-cloud-horizon-fade, and PMREM/material neutral-patch variants. Label these development-only variants; never keep a second production pipeline. Sample linear pre-tone-map radiance where feasible and final sRGB pixels; record line profiles above/below the horizon for multiple azimuths/heights, cloud alpha, context alpha, material luminance, PMREM capture count/duration and shader output. Identify which term causes each strip/seam/edge. A proposed technique must cite its isolated cause and show a minimal prototype before adoption.

**Stage B — one derived atmosphere state from the existing EnvironmentSnapshot.** Derive solar direction, cloud/overcast response, visibility coefficient, shared sky/horizon/path radiance, direct/ambient illumination and reflection invalidation inputs in the existing atmosphere owner. This is *rendering state*, not a second Weather or simulated clock. Use the current/replayed presentation snapshot at selected time. Define a daytime-valid mapping and explicit bounds; no camera-mode input and no hidden wall-time integration. A rain-only edit retains solar time; complete named presets may choose both. Preserve original weather numerical values and legacy attempt payloads unless a separately approved migration is necessary.

**Stage C — consistent optical transfer and geometry.** Define visibility as meteorological optical range for a dark target at 5% contrast: homogeneous reference extinction beta = ln(20)/visibility m⁻¹ and T(d)=exp(−beta d). The proposed shared surface equation in *linear* light is L_view=T(d)L_surface+(1−T(d))L_path(view,sun,cloud). It is a tractable local-air approximation, not full multiple scattering or measured humidity. Sky radiance and L_path at low elevation must be derived from the same sky/solar state; clouds use compatible path attenuation and sun direction. If the existing Sky plus a shared transfer function can satisfy the scenes, retain it. A replacement sky model, lookup texture or additional full-screen pass requires evidence that the existing path cannot meet the gates, explicit cost comparison and a contract/ADR revision before adoption. Do not simply raise FogExp2 density or paste sky color into fog.

The context turf must terminate without a rectangular edge or a camera-height alpha trick. First test whether consistent aerial perspective plus a bounded continuous context surface suffices. If it does not, a minimal noninteractive distant context silhouette/mesh may be proposed only after geometry, perspective, shadow and cost review; it cannot expand collision/mission bounds or impersonate surveyed features. Ground/Pilot/Follow/FPV/Overview must use the same world geometry and atmospheric law. Define no per-camera fog/exposure/terrain material overrides.

**Stage D — lighting, material and reflection closure.** A single solar direction governs sky sun, directional light, cloud illumination and shadow direction. Cloud cover attenuates direct and changes ambient in a declared monotonic mapping; it is not automatically the visibility coefficient. Keep fixed exposure .95 unless isolated color-space/tonal evidence shows it cannot satisfy all scenes; changing exposure requires a reviewed revision, not a per-weather patch. Preserve physically plausible concrete/turf/airframe roughness and existing wetness evolution; inspect before changing albedo or wet gloss. PMREM must capture the same atmosphere radiance state as the visible sky/clouds, with explicit invalidation for significant solar/cloud/rain-tinted-cloud/lighting changes and visibility if it changes captured radiance, bounded interval/coalescing and documented lag. Rain streaks need not appear in PMREM, but the existing rain-dependent cloud radiance cannot be omitted unless that coupling is deliberately replaced and validated. No every-frame cube capture.

**Stage E — temporal and phase integration.** Cloud transport stays the Phase 1 seed/time/offset model unless an isolated artifact proves a bounded correction is necessary; preserve replay/seek identity and reset behavior. Weather transitions follow the existing 2 s parameter response; derived light/optics remain continuous in current values. Phase 3 outputs a documented sky/illumination/extinction/visibility contract that Phase 4 rain can consume. Phase 4 must use the same current environment, linear-light path radiance, depth/extinction conventions and exposure, then add near streaks and distant precipitation without counting the same attenuation twice. Phase 3 does not implement the rain volume or change its trajectories.
